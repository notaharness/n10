# Cross-vendor pull request stacks

Design for [#162](https://github.com/notaharness/n10/issues/162). Status: proposed; this document adds no runtime behavior. Research snapshot: 2026-09-27. Provider documentation and tool source were inspected; no live merge, branch deletion, or Azure account experiment was performed.

## Decision and scope

Show PR dependencies automatically on GitHub and Azure DevOps. Start with discovery and navigation, then add explicit, resumable operations. A stack is a review dependency graph within a repository, not a new kind of agent session. Each PR keeps its own review, checks, worktree, and agent.

Support ordinary PRs whose targets are other PRs' source branches on both vendors. Also recognize GitHub's native stack membership when available. Do not require a stacking CLI, silently convert ordinary PRs into native stacks, or mutate another tool's metadata. Cross-vendor means equivalent capabilities on separate providers, not a single merge spanning GitHub and Azure repositories.

The deletion invariant is central: **never delete a remote branch while a known open PR targets it, or while the dependent-PR listing is incomplete**. Automatic provider deletion must also be accounted for before merging. A disappeared PR or branch does not establish that work was merged.

## Provider behavior and pain points

### GitHub: two distinct modes

GitHub now documents **native stacked PRs in public preview**. These are explicit stack objects, not merely matching branch names. They require same-repository branches and linear history; protections and Actions targeting the trunk apply across the stack. Cross-fork stacks are unsupported. This differs materially from ordinary dependent PRs, where targeting a feature branch does not itself establish trunk-equivalent checks. [Native requirements](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests), [creating/linking stacks](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-stacked-pull-requests).

Native merging selects a contiguous prefix, including every unmerged ancestor of the selected PR. GitHub documents rebasing and retargeting the next unmerged PR to the trunk afterward. It requires the asynchronous merge API; ordinary auto-merge is unsupported, while merge queues have stack semantics. [Native merge behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests).

Do not promise rollback of an entire native merge. The reference calls the operation atomic, but the troubleshooting page also describes partial success with already-landed PRs remaining merged. Reconcile each PR after completion, timeout, or failure. [Requirements](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests#merge-methods), [partial failure](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-stacked-pull-requests#merging-stopped-partway-through-the-stack).

For **ordinary dependent PRs**, GitHub documents retargeting open same-repository children when a merged PR's head branch is deleted. Its branch-management page also warns that deleting branches associated with open PRs can close them. These conditions are not a general transaction guarantee. [Branch deletion behavior](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository#deleting-a-branch).

The official CLI tracker contains a first-hand report of `gh pr merge --squash --delete-branch` closing a dependent PR through `base_ref_deleted`, rather than retargeting it. Reopening also failed in that report after branch restoration and subsequent head rewrites. Treat this as a reported failure mode, not a claim that every deletion behaves that way. It matches the class of incident n10 must prevent. Preserve original refs before attempting recovery; do not promise that every auto-closed PR can be reopened. [cli/cli#14223](https://github.com/cli/cli/issues/14223).

### Azure DevOps: ordinary PR operations

Azure Repos supports choosing and changing an active PR's target. The REST update API permits `targetRefName` when the retargeting feature is enabled. Target suggestions use a Git-history heuristic; they are not a declared dependency or a stack manager. [Target selection](https://learn.microsoft.com/en-us/azure/devops/repos/git/pull-request-targets?view=azure-devops), [retarget API](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/update?view=azure-devops-rest-7.1).

Completion offers merge, squash, rebase/fast-forward, and semi-linear strategies; source deletion is a completion option. Auto-complete waits for required policies. Policies apply to the PR's actual target branch, so a child targeting an unprotected feature branch may lack the trunk's gates. Retargeting needs a fresh policy/merge evaluation. [Completion options](https://learn.microsoft.com/en-us/azure/devops/repos/git/complete-pull-requests?view=azure-devops), [branch policies](https://learn.microsoft.com/en-us/azure/devops/repos/git/repository-settings?view=azure-devops#branch-policies).

No native stack object, cascading merge, or guaranteed automatic child retargeting was found in the cited Azure contracts. Microsoft's retarget feature explicitly discusses handling targets that were merged or deleted. The fate of an active child after target deletion—still active but broken, abandoned, or otherwise unavailable—was **not verified live**. Do not import GitHub's auto-close behavior as an Azure fact. Model a missing target and observed PR status separately; prevent deletion and test the actual deployment before enabling managed landing. Azure Services and Server versions may differ. [Microsoft's retarget scenario](https://learn.microsoft.com/en-us/azure/devops/server/release-notes/azuredevops2019#change-the-target-branch-of-a-pull-request).

### Costs shared by both vendors

Retargeting changes the review comparison; it does not rewrite Git history. Squashing a parent creates a new commit, so the child's old parent commits can remain in its comparison and create duplicate diffs or conflicts. Restacking must replay only the child's commits using a recorded old boundary, not a freshly guessed merge-base after the parent was rewritten. Git documents this use of `rebase --onto`. [Git rebase](https://git-scm.com/docs/git-rebase#_examples).

Pushing a repaired head or changing its target can require new checks/reviews. A green ancestor is not approval of its descendants, and a green child against a feature branch is not proof of readiness for trunk. Showing dependencies reduces review scope, but it creates maintenance work whenever a lower layer changes.

## Model and discovery

A proposed browser-safe `StackSnapshot` contains PR nodes, observed dependency edges, optional native membership, freshness/completeness, and diagnostics. Mutation journals are separate Node-side records.

| Element            | Required information                                                                                                                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PR identity        | Provider, host/organization, immutable target repository ID, and PR number/ID. Display URLs and checkout paths are not identity.                                                                         |
| Branch identity    | Repository ID plus full ref such as `refs/heads/feature/a`; retain case and slashes. Source repository may differ from target repository for forks.                                                      |
| Node               | Source/target identities and SHAs; open/merged/closed-or-abandoned/unknown; draft, provider readiness, URL; last successful observation.                                                                 |
| Observed edge      | Child targets parent's source ref in the same ref-owning repository. Evidence includes both PR revisions and observation time. Multiple matching parents are ambiguous.                                  |
| Managed dependency | Explicit parent PR identity plus the old parent commit contained in the child, recorded when the relationship is adopted. Survives a temporary retarget to trunk; distinct from the current review base. |
| Native membership  | Provider stack ID, trunk, ordered PR identities, and capability/version observation. Native membership conflicts with inferred refs are diagnostics, not silently repaired.                              |
| Operation journal  | Operation ID, actor/machine, repository, approved plan, original/expected refs, per-step outcomes, and recovery state. Never credentials.                                                                |

Discovery builds an index of PRs by source repository/ref, then resolves targets. Ordinary chains may fan out; represent them as a forest, not an arbitrary numbered linear stack. Cycles, duplicate source PRs, inaccessible forks, and partial listings produce explicit unresolved edges. A long-lived target with no matching PR is a possible trunk, not proof of a missing parent. Fetch known former parents by ID when an observed node disappears.

Do not infer dependencies from titles, labels, branch prefixes, PR numbers, or commit overlap alone. Tool metadata can suggest an external relationship but cannot authorize writes. Git ancestry validates a managed operation, not the existence of a review relationship. Closed parents remain visible as blockers/history; a missing list row is `unknown` until a direct read establishes status.

Persist managed lineage and journals in n10's per-repository state, keyed by provider repository identity. Anchor a managed stack with a stable local ID; keep merged ancestors as history so the ID does not change on each landing. Read-only inferred views need no published metadata. Do not write PR-body navigation comments by default. n10 does not need everyone on a team to install a tool to see a stack.

### Fit with the codebase

At baseline `b8b5e2ea`, [`PullRequestInfo` and `VcsProvider`](../../libs/vcs/core/src/lib/types.ts) have source/target branch strings but no repository-qualified refs, lifecycle state, native stack capability, or retarget/merge operations. `BranchPrMap` is keyed by source branch and cannot represent multiple PRs from that branch. Add a lossless list for stack discovery; retain the map only as a compatibility projection.

The [GitHub provider](../../libs/vcs/github/src/lib/provider.ts) lists open PRs involving the configured user, which can omit a parent or another author's dependent child. The [Azure provider](../../libs/vcs/azure-devops/src/lib/provider.ts) requests active repository PRs but its current listing does not express pagination completeness. Neither result is sufficient evidence for safe remote deletion. Add paginated, repository-wide dependency discovery without the personal inbox filter, plus direct PR-by-ID reads. Keep incomplete data visible without claiming the graph is complete.

Put provider contracts/transports in `libs/vcs`, graph construction and operation sequencing in `libs/core`, and shared React controllers in `libs/app-core`. Expose immutable graph data through Desktop's host contract; both Desktop and TUI consume the same result. Reuse the shared PR cache and its stale/error semantics rather than adding independent sidebar polls. Managed operations require fresh reads, not cached absence.

Connect the dependency guard to [`sweepMergedBranches`](../../libs/core/src/lib/sync/remote-sync.ts) and [`removeWorktree`](../../libs/core/src/lib/session/remove-worktree.ts) during implementation. Distinguish local worktree cleanup, local ref deletion, and remote ref deletion. A merged parent's saved ref/boundary may still be needed for restacking.

## Desktop and TUI experience

Keep existing review categories and their counts. Add a **Stack** badge to participating PR rows; activating it reveals the component, including context PRs outside the user's inbox without counting them as assigned reviews. The stack is secondary navigation beside the selected PR, not a replacement for the review workspace.

Desktop uses existing disclosure rows, status icons, and a compact details panel. TUI uses the existing selectable-list/focus model, indented rows, and textual status. Add named actions to the keybinding registry; choose bindings against existing presets during implementation. No mouse-only action, custom terminal cursor positioning, or implied drag-to-rebase interaction.

```text
Stack · main                 Updated 12 seconds ago
  #41  Shared parser         Approved · checks passed
    #42  GitHub adapter      Waiting on #41 · checks pending
    #43  Azure adapter       Waiting on #41 · changes requested
```

Each row shows PR number/title, provider state, and dependency status independently. A selected child says **Targets feature/parser · Depends on #41**. The detail view offers **Open PR**, **Open worktree**, **Previous parent**, and **Next dependent**; fan-out requires choosing a child. Selecting a PR opens its existing review/terminal context without duplicating sessions. Native stacks get **GitHub stack**; externally managed ones name the tool when verified.

Later actions are **Change target…**, **Create child PR…**, **Restack descendants…**, and **Merge bottom PR…**. A native prefix action must say **Merge 3 PRs into main…** and list every affected PR. The confirmation previews target/ref changes, force-pushes, worktrees involved, and deferred cleanup. Opening or refreshing a stack never changes branches.

| State                                 | User-facing behavior                                                                                                       |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Parent updated                        | “Parent changed · Restack needed” only when ancestry was checked; otherwise “Check branch ancestry”.                       |
| Parent merged, child still targets it | “Parent merged · Change target needed”; show destination from observed parent history.                                     |
| Missing target or auto-closed child   | “Target branch missing · Recovery needed”; retain PR link and last known refs.                                             |
| Stale/incomplete discovery            | “Stack data may be incomplete · Retry”; disable operations requiring complete dependents.                                  |
| Interrupted operation                 | Show completed and pending steps, **Resume**, and the available local rollback scope. Never label a remote merge undoable. |
| Managed elsewhere                     | Navigation and **Open in provider/tool**; no competing background restack.                                                 |

The PR diff stays relative to its current provider base. Label a future cumulative-to-trunk view separately. Agent review prompts identify the selected PR, its parent, and review base; reviewing one layer does not implicitly review or approve ancestors.

## Provider operation contracts

Add capability-specific operations: `listStackCandidates`, `getPullRequest`, `getRef`, `retargetPullRequest`, `createPullRequest`, `mergePullRequest`, `pauseAutomaticLanding`, and guarded `deleteRef`. Native stack operations are separate. Capabilities distinguish supported, unsupported, unauthorized, and unknown; a 404 alone cannot distinguish a hidden repository from an unavailable feature.

All mutations accept explicit repository coordinates and expected observed state. A client preflight is not a server-side compare-and-swap: where a provider has no conditional retarget, re-read immediately before and after, detect divergence, and stop. Return structured outcomes including pending/unknown, not just a successful HTTP status.

| Operation         | GitHub                                                                                                                                                          | Azure DevOps                                                                                                                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Discover          | Paginate `GET /repos/{owner}/{repo}/pulls?state=open`; retain head/base repo/ref/SHA. Direct PR GET supplies lifecycle evidence.                                | Paginate repository `pullrequests` with active status and `$top`/`$skip`; retain `forkSource`, full refs, merge-source/target commits and status. Direct GET known missing IDs.             |
| Retarget          | `PATCH .../pulls/{number}` with `base`; destination must exist in that target repository. Re-read open state/base/head.                                         | `PATCH .../pullrequests/{id}?api-version=7.1` with `targetRefName`; feature and permission dependent. Re-read target and refreshed merge/policy state.                                      |
| Create child      | POST pull request with explicit head/base; first push a child branch based on the selected parent.                                                              | POST pull request with explicit `sourceRefName`/`targetRefName`; no target-guess heuristic.                                                                                                 |
| Ordinary merge    | `PUT .../pulls/{number}/merge`, expected `sha`, allowed merge method. Confirm `merged`, not merely closed.                                                      | PATCH completion status/options; use explicit strategy, `deleteSourceBranch: false`, no policy bypass. Confirm completed status and merge result; auto-complete requested is not completed. |
| Delete remote ref | Prefer Git transport with an explicit expected-OID lease. REST DELETE exists but lacks an expected-OID body; a read then DELETE is racy.                        | Refs update supports `oldObjectId`; deletion sets `newObjectId` to the zero OID. Check each result's success/error, not only HTTP 200.                                                      |
| Native stacks     | Read membership from PR `stack`/Stacks API; ordered creation/extension uses dedicated REST endpoints. Native merge uses `/merge-async` and its result resource. | No equivalent capability established by this research; ordinary graph/operations remain available.                                                                                          |

Sources for this mapping: [GitHub PR REST](https://docs.github.com/en/rest/pulls/pulls), [GitHub refs](https://docs.github.com/en/rest/git/refs), [native stack API](https://docs.github.com/en/rest/pulls/stacks), [native API overview](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests-apis-and-webhooks), [Azure list](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/get-pull-requests?view=azure-devops-rest-7.1), [Azure update](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/update?view=azure-devops-rest-7.1), [Azure create](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/create?view=azure-devops-rest-7.1), [Azure refs](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/refs/update-refs?view=azure-devops-rest-7.1).

Azure completion should send the observed `lastMergeSourceCommit`, as Microsoft's CLI does. Its exact stale-head rejection contract must still be tested before managed landing; the update page's writable-field list does not establish a CAS guarantee for that field. GitHub's ordinary merge SHA guard does not guard all ancestors of a native prefix. Native capability tests must establish stale-prefix behavior before enabling that action.

Pausing automatic landing is a distinct, permission-checked operation. GitHub exposes GraphQL `disablePullRequestAutoMerge` and `dequeuePullRequest`; read back both states before editing a queued child's target. Microsoft's Azure CLI cancels auto-complete by updating `autoCompleteSetBy.id` to the zero UUID. Follow that wire contract and verify cancellation on the supported deployment. Do not resume automatic landing until the repaired PR has been rechecked and the user approves it. Third-party merge queues need their own verified cancellation capability; otherwise block the plan. [GitHub mutations](https://docs.github.com/en/graphql/reference/pulls#disablepullrequestautomerge), [Microsoft's CLI implementation](https://github.com/Azure/azure-devops-cli-extension/blob/4d49a4b367fdba19442bfccf07e9516a8a3dd857/azure-devops/azext_devops/dev/repos/pull_request.py#L328-L344).

## Safe operation sequence

For an ordinary stack `main <- A <- B`, with possible siblings of B:

1. **Plan from fresh state.** List all dependent PRs, read ref OIDs, policies, native/tool ownership, auto-merge/auto-complete state, and repository automatic branch-deletion settings. Record every direct child, intended destination, and original ref in the journal. Refuse unsupported or incomplete plans.
2. **Protect dependents before landing.** Prefer retaining A remotely through merge and repair. On GitHub, omitting `--delete-branch` does not disable [repository-level auto-deletion](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches). If A cannot be retained, offer an explicit retarget-before-merge plan for every direct child to A's target. Pause those children's pending automatic merges and dequeue them first; do not silently change repository-wide settings. If they cannot be paused, block this plan. The temporary wider diff is shown, and the managed dependency on A remains recorded.
3. **Merge only the eligible bottom PR.** Use provider policy enforcement and the reviewed head. Read back actual merge status/result. On a timeout, reconcile before retrying. If A was already merged externally, skip the merge and repair from the recorded evidence. Never merge B into A as a shortcut to landing B on main.
4. **Repair all affected children.** Retarget any child still based on A to the confirmed surviving destination; do not overwrite an external target change. For rewritten parent history, replay each child's own commits onto the new parent/trunk using its saved old boundary. Work bottom-up through descendants. If history already has the new parent as an ancestor, avoid rewriting unnecessarily.
5. **Publish and verify.** Push each changed ref with `--force-with-lease=<ref>:<expected-old-oid>`; an implicit lease based on a background-updated tracking ref is insufficient. Re-read targets, heads, PR states, and policies. A new author push invalidates the plan. Show changed review/CI requirements and wait for fresh results before another merge. [Explicit Git leases](https://git-scm.com/docs/git-push#Documentation/git-push.txt---force-with-lease).
6. **Clean up last.** Freshly enumerate all open dependents again. Only after every child is safely retargeted and repair is complete may an explicit cleanup delete A's remote ref, using its expected OID. Keep journals/backup refs through recovery. Local worktree removal remains a separate action with normal dirty-work/session checks.

No sequence of ordinary PR API calls is an atomic transaction across all refs and PRs. Another actor can create a dependent between listing and deletion. Default managed landing therefore **retains branches**; destructive cleanup requires a final review and remains best-effort under concurrent actors. There is no unattended “delete everything merged” stack action.

Restacking uses an operation lock per repository, saved refs, and a clean dedicated worktree where possible. Never reset a worktree used by an agent or another checkout. Active, dirty, or externally moving worktrees stop the plan; stopping an agent requires the normal user action. Resolve conflicts through explicit continue/abort. `abort` can restore unpublished local refs; after publication, recovery is a new reviewed plan, not an automatic force-push rollback.

A managed operation survives app restart through its journal. On resume, reconcile actual refs and PRs before each remaining step. Both shells show the same operation ID/status. Multiple n10 instances share a local lock; separate machines still rely on expected ref OIDs and conflict detection. No background poll initiates retargeting, rebasing, or merging.

For GitHub native stacks, use the native prefix operation instead of the ordinary retarget loop. Verify membership and all affected PRs before submission, reconcile server rebases/retargets afterward, then offer local synchronization. Do not race server history changes with a local restack. External-tool stacks delegate to their owner until a user explicitly adopts a verified ordinary/native representation.

## Failure and recovery rules

| Failure                                              | Required response                                                                                                                                                                                                 |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Parent closes without merging                        | Keep children blocked; offer reopen in provider or a reviewed move to another parent. Do not infer merged from absence.                                                                                           |
| Branch deleted; child closes/abandons                | Retain the original PR and ref evidence. Offer restoration/reopen only when the provider supports it; if impossible, explicitly create a replacement linked to the old PR. Never silently discard review history. |
| Parent force-pushed, old boundary unavailable        | Stop. Recover the saved ref or have the user choose/verify the child-only commit range; do not replay guessed ancestor commits.                                                                                   |
| Rebase conflict or dirty worktree                    | Pause with the exact worktree and files. Preserve branch snapshots; no automatic stashing/reset of agent work.                                                                                                    |
| Lease rejects or target changes                      | Re-read and rebuild the plan. Do not weaken the lease or overwrite the external edit.                                                                                                                             |
| Permission denial, rate limit, offline, partial page | Keep stale topology with the error. Back off reads; block writes requiring missing evidence. Retry from the journal.                                                                                              |
| Crash after push/retarget/merge                      | Check whether that exact step took effect before retrying; retain successful remote steps and report partial completion.                                                                                          |
| Checks/approvals become stale; queue ejects a PR     | Display current provider gates and stop downstream landing. Never bypass policies to keep the stack moving.                                                                                                       |
| Fork, duplicate parent, cycle, native mismatch       | Display unresolved/externally managed topology. No destructive action until ambiguity is resolved.                                                                                                                |

The live matrix must cover GitHub ordinary versus native stacks; merge/squash/rebase; server auto-delete on/off; explicit REST/Git deletion; child auto-merge; changed heads; and interrupted responses. For Azure, cover each supported deployment/version, completion strategy, `deleteSourceBranch`, auto-complete, target deletion, retarget and restart-merge behavior, and stale-head completion. Record whether children remain open, retarget, close/abandon, and can be recovered. Use disposable repositories and explicit opt-in credentials; never production PRs. Fake tests verify n10 behavior, not undocumented provider guarantees.

Phase 1 delivers the original discovery goal of #162. Creation, restacking, landing, third-party adapters, and remote cross-machine execution should be separate implementation issues. Multi-parent dependencies, cross-repository landing, synthetic review branches, automatic policy changes, and a new hosted merge service are outside this design.
